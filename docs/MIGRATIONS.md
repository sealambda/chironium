## Overview

Ash Framework generates database migrations automatically based on your resource definitions. Unlike traditional Ecto migrations where you write SQL manually, Ash:

1. Tracks **resource snapshots** — a JSON representation of your resource at a point in time.
2. **Diffs** your current resource definitions against the last snapshot.
3. **Generates migrations** based on the differences.

Both migrations and snapshots **must be committed to version control**.

---

## Key Concepts

### Resource Snapshots

Located in `priv/resource_snapshots/repo/`, these JSON files represent the state of each Ash resource at the time a migration was generated.

**Purpose**: Ash uses these to calculate what changed between the last migration and your current resource definition.

**Important**: Without snapshots, Ash cannot determine incremental changes and would regenerate the entire schema.

### Migrations

Located in `priv/repo/migrations/`, these are standard Ecto migration files generated by Ash.

**Purpose**: Define the exact SQL operations to transform the database schema.

### Development vs. Named Migrations

| Type            | Command                  | Use Case                          |
| --------------- | ------------------------ | --------------------------------- |
| **Development** | `mix ash.codegen --dev`  | Active iteration, experimenting   |
| **Named**       | `mix ash.codegen <name>` | Feature complete, ready to commit |

## Development Workflow

### 1. Active Development (Iterating)

When actively working on a feature and making frequent changes:

```bash
# Make changes to your Ash resources
# Then generate and apply development migrations
mix ash.codegen --dev
mix ash.migrate
```

You can run `--dev` multiple times. Each run creates a timestamped development migration.

### 2. Feature Complete (Ready to Commit)

When your feature is complete and tested:

```bash
# Squash all dev migrations into a single named migration
mix ash.codegen add_customer_profiles
mix ash.migrate
```

**What happens**:

1. All `--dev` migrations are rolled back.
2. Changes are squashed into a single migration with your chosen name.
3. A clean snapshot is created.
4. The new migration is applied.

### 3. Clean Up Snapshots (Optional)

If you have multiple snapshots per resource from iterations:

```bash
mix ash_postgres.squash_snapshots
```

This keeps only the latest snapshot per resource.

### 4. Commit

```bash
git add priv/repo/migrations/
git add priv/resource_snapshots/
git commit -m "feat(db): Add customer profiles migration in priv/repo/migrations/..."
```

## Committing Migrations

### What to Commit

| Path                                         | Commit? | Notes                  |
| -------------------------------------------- | ------- | ---------------------- |
| `priv/repo/migrations/*.exs`                 | ✅ Yes  | All migration files    |
| `priv/resource_snapshots/**/*.json`          | ✅ Yes  | All resource snapshots |
| `priv/resource_snapshots/**/extensions.json` | ✅ Yes  | Extension snapshots    |

### Commit Message Convention

Follow the project's commit standards:

```sh
feat(db): Add customer profiles table in priv/repo/migrations/20260123120000_add_customer_profiles.exs
```

For migrations affecting authentication:

```sh
feat(auth): Add user tokens table in priv/repo/migrations/20260123120000_add_user_tokens.exs
```

## Multi-Environment Strategy

### Environment Responsibilities

| Environment | Generate Migrations?  | Run Migrations?  |
| ----------- | --------------------- | ---------------- |
| Local Dev   | ✅ Yes                | ✅ Yes           |
| CI          | ❌ No (validate only) | ✅ Yes (test DB) |
| Staging     | ❌ No                 | ✅ Yes           |
| Production  | ❌ No                 | ✅ Yes           |

### The Golden Rule

> **Never generate migrations in staging or production. Only run them.**

All environments run the same committed migrations in the same order.

### Deployment Flow

```txt
Local Dev                    CI                      Staging                 Production
    │                        │                          │                        │
    ├─ Generate migrations   │                          │                        │
    ├─ Test locally          │                          │                        │
    ├─ Commit & push ────────┼──► Validate migrations   │                        │
    │                        ├──► Run tests             │                        │
    │                        ├──► Pass ─────────────────┼──► Deploy              │
    │                        │                          ├──► mix ash.migrate     │
    │                        │                          ├──► Verify ─────────────┼──► Deploy
    │                        │                          │                        ├──► mix ash.migrate
    │                        │                          │                        └──► Monitor
```

## Handling Mistakes

### Scenario 1: Mistake Caught Before Commit

**Situation**: You generated a migration but haven't committed yet.

**Solution**: Simply fix your resource and regenerate.

```bash
# Fix your Ash resource definition
# Then regenerate
mix ash.codegen --dev
mix ash.migrate
```

### Scenario 2: Mistake Committed but Not Deployed

**Situation**: Migration committed to `develop`, not yet in `staging` or `production`.

**Solution A — Amend (if recent and no one pulled)**:

```bash
# Fix your resource
mix ash.codegen --dev
mix ash.migrate

# Amend the commit (only if not pushed or team hasn't pulled)
git add priv/
git commit --amend
git push --force-with-lease origin develop
```

**Solution B — New corrective migration (preferred)**:

```bash
# Fix your resource
mix ash.codegen fix_customer_profiles_typo
mix ash.migrate

# Commit the fix
git add priv/
git commit -m "fix(db): Correct customer profiles column type in priv/repo/migrations/..."
git push origin develop
```

### Scenario 3: Mistake Deployed to Staging (Not Production)

**Situation**: Bad migration ran in staging, production is clean.

**Solution**: Create a corrective migration.

```bash
# 1. Fix your Ash resource locally
# 2. Generate a new migration that corrects the issue
mix ash.codegen fix_staging_migration_issue
mix ash.migrate

# 3. Commit and deploy
git add priv/
git commit -m "fix(db): Correct migration issue from staging in priv/repo/migrations/..."
git push
```

When deployed to staging, the new migration will:

- Apply the fix on top of the broken state.

When deployed to production (which never had the bug):

- Both migrations run, but the "fix" migration will be a no-op or safe addition.

### Scenario 4: Mistake Deployed to Production

**Situation**: Bad migration ran in production.

**Solution**: **Never edit or delete existing migrations.** Always move forward.

```bash
# 1. Assess the damage — what exactly is wrong?
# 2. Fix your Ash resource to the CORRECT state
# 3. Generate a corrective migration
mix ash.codegen fix_production_issue
mix ash.migrate

# 4. Test thoroughly locally and in staging
# 5. Deploy to production
```

**Critical rules**:

- ❌ Never delete a migration that has run in any environment.
- ❌ Never edit a migration that has run in any environment.
- ✅ Always create new migrations to fix issues.

### Scenario 5: Need to Remove a Column/Table That Was Just Added

If you added something by mistake and need to remove it:

```bash
# 1. Remove the attribute/resource from your Ash definitions
# 2. Generate the "removal" migration
mix ash.codegen remove_accidental_column
mix ash.migrate

# Ash will generate a migration that drops the column/table
```

### Scenario 6: Divergent Environments

**Situation**: Staging and production have different schemas due to a mistake.

**Solution**: Reconciliation migration.

```bash
# 1. Document exact differences between environments
# 2. Create a migration that handles both cases

# In the migration, you can use conditional logic:
defmodule MyApp.Repo.Migrations.ReconcileSchemas do
  use Ecto.Migration

  def up do
    # Check if column exists before adding
    if !column_exists?(:users, :new_column) do
      alter table(:users) do
        add :new_column, :string
      end
    end
  end

  def down do
    alter table(:users) do
      remove :new_column
    end
  end

  defp column_exists?(table, column) do
    query = """
    SELECT column_name
    FROM information_schema.columns
    WHERE table_name = '#{table}' AND column_name = '#{column}'
    """
    case repo().query(query) do
      {:ok, %{num_rows: n}} when n > 0 -> true
      _ -> false
    end
  end
end
```

**Note**: For complex reconciliation, you may need to write a manual migration instead of using Ash's generator.

## CI/CD Integration

### Validation in CI

Add this check to ensure migrations are up-to-date:

```bash
# Fails if current resources don't match committed migrations
mix ash_postgres.generate_migrations --check
```

### Example GitHub Actions Step

```yaml
- name: Validate migrations
  run: mix ash_postgres.generate_migrations --check

- name: Run migrations
  run: mix ash.migrate
  env:
    DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}
```

### Pre-commit Hook (Optional)

Add to `.git/hooks/pre-commit`:

```bash
#!/bin/bash
mix ash_postgres.generate_migrations --check --quiet
if [ $? -ne 0 ]; then
  echo "Error: Uncommitted migration changes detected."
  echo "Run 'mix ash.codegen <name>' to generate migrations."
  exit 1
fi
```

## Common Commands

### Daily Development

```bash
# Generate development migration (iterating)
mix ash.codegen --dev

# Apply pending migrations
mix ash.migrate

# Generate named migration (feature complete)
mix ash.codegen add_feature_name

# Reset database (drop, create, migrate, seed)
mix ash.reset

# Setup database (create if needed, migrate, seed)
mix ash.setup
```

### Maintenance

```bash
# Squash snapshots (keep only latest per resource)
mix ash_postgres.squash_snapshots

# Check if migrations need to be generated
mix ash_postgres.generate_migrations --check

# Dry run — see what would be generated
mix ash_postgres.generate_migrations --dry-run

# Rollback last migration
mix ash_postgres.rollback

# Rollback to specific version
mix ash_postgres.rollback --to 20260122200830
```

### Inspection

```bash
# List migration status
mix ecto.migrations

# Show pending migrations
mix ecto.migrations --pending
```

## Troubleshooting

### "No migrations to generate"

Your resources match the snapshots. Either:

- No changes were made.
- Changes were already captured in a previous migration.

### "Migration already exists with that name"

Choose a different name or let Ash auto-generate with `--dev`.

### Snapshot conflicts after merge

If you get conflicts in snapshot files after merging branches:

```bash
# 1. Accept the incoming changes (or resolve manually)
# 2. Regenerate migrations
mix ash.codegen merge_branch_changes
mix ash.migrate
```

### Database is ahead of migrations

If your local DB has changes not in migrations (manual SQL, etc.):

```bash
# Option 1: Reset completely
mix ash.reset

# Option 2: Generate migration to match current state
# (May require manual adjustment)
mix ash.codegen sync_manual_changes
```

### "Relation does not exist" errors

Migrations may be running out of order. Check:

1. Migration timestamps are correct.
2. Dependencies between migrations are respected.
3. Run `mix ash.reset` for a clean slate.

## Best Practices Summary

1. **Use `--dev` during active development** — Iterate freely without noise.
2. **Name migrations when feature-complete** — `mix ash.codegen add_user_roles`
3. **Never edit deployed migrations** — Always create corrective migrations.
4. **Commit both migrations and snapshots** — They work together.
5. **Validate in CI** — `mix ash_postgres.generate_migrations --check`
6. **One migration per commit when possible** — Matches project commit standards.
7. **Test migrations locally before pushing** — Run `mix ash.reset` to verify.
8. **Squash snapshots periodically** — Keeps the repo clean.
